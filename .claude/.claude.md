# File structure

```
Family name
  ├── Documents  --> Family User Manual (pdf)
  ├── iodefine   --> CMSIS iodefine header file (.h)
  ├── nuttx_hw_headers --> OUTPUT folder for generated NuttX headers (.h)
  ├── svd  --> SVD file (.svd)
  └── zone --> FSP zone file, one per Part Number (.rzone)
```

`nuttx_hw_headers/` is generated output, never hand-copied from another family.

# Tools

- `svdtoheaders/svdtoheaders` — legacy generic SVD-only dumper. **Never modify
  or import it** (separate git repo; no `__main__` guard). Superseded by:
- `gen_ra_headers.py` — the real generator. Requires `.venv` (`xmltodict`).
  ```
  gen_ra_headers.py -v -o --svd F.svd --zone F.rzone --iodefine F_iodefine.h \
    --memorymap OUT/xxx_memorymap.h --memorymap-path arch/.../xxx_memorymap.h \
    --peripheral "OUT/xxx_sci.h:arch/.../xxx_sci.h:SCI:SCI0,SCI1,SCI2=SCI0,..."
  ```
  `--peripheral` spec = `OUTFILE:PATH:FAMILYPREFIX:INSTANCES`, INSTANCES are
  comma-separated `NAME` or `NAME=TEMPLATE` (override for instances with no
  SVD entry of their own).

# Critical facts (apply to any RA chip, not just RA8M1)

1. **`iodefine.h`, not `.rzone`, is the memorymap's source of truth.**
   `.rzone` is scoped to one physical package/pin-count variant and silently
   omits instances (e.g. no `ADC1` in any RA4M1 zone file). `iodefine.h` is
   full-chip and matched the RA4M1 hand-written memorymap 105/106.
2. **Peripheral names diverge across `.svd` / `.rzone` / `iodefine.h` for the
   same block** (e.g. `0x4001E000` = `SYSTEM` in zone/iodefine, `SYSC` in
   RA8M1's SVD). **Base address is the only reliable join key.**
3. **SVD `@derivedFrom` encodes instance-array families** (PORT0-14, SCI0-9,
   GPT0-13, ...). Follow the chain to the node that owns `<registers>` — that
   is the register template. A family can have >1 template flavor (RA4M1
   SCI0/1 have FIFO regs, SCI2/9 don't); instances are not always identical.
4. **Some instances have no SVD entry at all** (RA4M1 SCI3-8, RA8M1 SCI_B5-8)
   — nothing to derive from automatically. Must use an explicit
   `NAME=TEMPLATE` override; the tool errors rather than guessing.
5. When merging a family's register table, **dedup by register name, not by
   offset** — multiple real registers can legitimately share an offset
   (mode-alias views, e.g. `TDRHL`/`FTDRHL`). Deduping by offset silently
   drops one; the generator keeps all of them (superset of what hand-written
   files curated — safe, if slightly more verbose).
